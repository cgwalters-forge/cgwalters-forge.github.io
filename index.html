cgwalters-forge

Where cgwalters-bot, a semi-autonomous agent account operated by cgwalters, does its work, and the tools that run it.

The organization holds two kinds of repositories. Forks of upstream projects are where the bot proposes changes for cgwalters' review before anything goes upstream; the organization README describes that. First-party projects are the harness itself: the pieces that decide what the bot works on, run it, and check what it produces. This page is about how those pieces fit together.

One piece of work, end to end

There is no long-running agent session. Everything happens in GitHub Actions runs, and every decision leaves a record on an issue or pull request.

  1. The board holds the work. Issues sit on an organization project board with a priority and a status. cgwalters sets direction by commenting, prioritizing, and answering questions the bot files when it needs a decision.
  2. A poll schedules it. A scheduled workflow in the tracker runs agent-board, which reads the board, posts a job plan on an issue, and dispatches one run per plan. It holds work back while an inference pool is near its usage limit, or while another open bot pull request overlaps it.
  3. agentic-job runs the agent. The dispatch calls a reusable workflow, which runs a coding agent through agentic-job on a runner hardened by secure-host. The agent gets the repository and a model endpoint, but not the job's GitHub token. Model credentials stay behind a broker that admits only the organization's workflows.
  4. Its outputs are checked, not trusted. The agent proposes a branch, a comment or a board change. A separate job validates the proposal against the run's bounds before pushing or posting anything as the bot.
  5. An independent review gates the merge. A review workflow runs a separate agent against the pull request. If it approves, the pull request goes into the merge queue. If it asks for changes, the poll dispatches a fix round on the same branch.
  6. A supervisor watches the loop. A separate scheduled agent reads health checks for runs, pacing, the queue and stuck items. It files issues for what it finds, and may dispatch triage, all within daily caps.

Upstream contributions are still promoted by hand: cgwalters takes an approved change from a fork to the upstream project. A hosted promotion step is planned.

Hardening that isn't only for agents

An agent job is just a CI job that runs untrusted code, and so is a dependency's build script or a test suite. The rule here is that a sandboxing technique doesn't count as done until plain, deterministic CI can use it too. So host hardening lives in a standalone secure-host action that any workflow can call. Its BPF LSM policy refuses another user's change to a world-writable file when the change happens, and its egress write policy is opt-in. agentic-job builds on secure-host instead of carrying its own copy.

Compared with GitHub Agentic Workflows

The design borrows heavily from gh-aw: agents run as Actions jobs, and they write only through validated safe outputs. The differences are support for containers and self-hosted runners, a board-driven scheduler rather than one workflow per task, and hardening that applies to the rest of CI. agentic-job's README explains the choice.
